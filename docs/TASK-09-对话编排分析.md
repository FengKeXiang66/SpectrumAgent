## 2. 根因：编排打转

### 2.1 主因——v1 提示词在主动制造追问

`skill.py:12-24` 的 v1 提示词里有两条直接导致实录表现：

```
3. 不确定就反问：参数缺失或意图不明时向用户提问，禁止取默认值替用户决定。
5. 只说标识不说路径：对话中只出现数据集、区域、版本的 id。
```

用户已经说了"参数均按默认进行处理"，但规则 3 不区分"用户没给"和"用户已授权默认"，助手仍按"缺失"处理 → 继续追问。
规则 5 让助手只能吐 UUID → 用户看不懂 → 只能回"第一个""081 开头" → 歧义 → 再追问。闭环形成。

v2 提示词（`skill.py:27-51`）已经逐条改掉：默认授权、D 短引用、`resolve` 消歧、禁止重复询问已知信息、连续调用直到完成。

### 2.2 v1 执行器是"一锤子买卖"

`state.py:407-533` 的 `_generate`：解析 → 执行工具 → 解读 → 结束。
关键在 `state.py:525`：`self.llm.chat(messages, None)` —— **解读阶段传的 tools 是 `None`**，工具不可用，所以拿到数据集列表后只能说话，不能顺势查标签、生成分割。

v2 `workflow.py:246` 用 `calls = None` 回到 `while True` 重新请求模型，形成 observe-act 循环，并配了预算（`MAX_WORKFLOW_BATCHES=16` / `MAX_WORKFLOW_STEPS=32`）、无进展检测（`workflow.py:230` 相同调用重复即 `AGENT_NO_PROGRESS`）、目标一致性校验（`workflow.py:195` `TASK_DATASET_MISMATCH`）。

### 2.3 v1 工具链断点

| 环节 | v1 状态 | v2 状态 |
|---|---|---|
| 数据集列表 | 只返回 UUID 串（`tools/__init__.py:271-274`） | 返回 `dataset_i_name` + `D{i}` 短引用（`workflows.py:101-110`） |

### 3.2 序号错位（原分析完全没提）

```
SELECT id FROM dataset_registry ORDER BY id      -- v1 工具   → 第1个 = 081c0cba
SELECT id FROM dataset_registry ORDER BY rowid   -- v2 工具/导入序 → 第1个 = 880b040a
```

v1 `tools/__init__.py:273` 用 `ORDER BY id`（UUID 字典序），v2 `workflows.py:102` 用 `ORDER BY rowid`（导入顺序）。
实录里助手认定"第一个 = 081c0cba"正是 v1 的字典序结果。

**口径收紧（第二轮复核）**：这只能证明跨列表错位的**风险**，不能单凭 SQL 顺序断定那次一定选错了数据——用户也可能就是指助手刚列出的那一项。真正的判定要靠共享目录快照（见 §7.2）。

此外 UI 顺序根本不由 SQL 决定：`src/components/datasets/types.ts:30` 的 `mergeRecords` 用 `Map` 按 id 合并，旧记录保持原位、新导入追加在后。所以**界面顺序、v1 工具顺序、v2 工具顺序是三份可能互不相同的列表**。

## 5. 一个必须说清的边界

**"PP，其余为背景"不能纯靠对话闭环。**

谱相似扩散（`annotation/engines/diffusion.py`）是"从种子出发按光谱相似性扩散"，它不判定种子是不是 PP；SLIC 只做超像素分割，也不识别材质。
v2 的处理是对的：`workflows.py:272-274` 无手势时返回 `need_seed` 并明确说明"分割和原谱相似扩散不能自动判断 PP 等材质"，不编造。

要让纯对话更顺，只能三选一：

1. 接入已验证的材料分类模型；
2. 提供适配本批数据的参考光谱；
3. 系统生成可视候选，用户在画布指认后对话确认。

在给出上述任一依据前，**助手只应补问这一项**，而不是重问数据集、操作类型和全部参数。这是当前 v2 已经做到、需要在验收里重点守住的行为。

## 7. 第二轮复核：补充与修订

### 7.1 发布产物核对（修订 §0 结论 1 的表述）

复核称发布包里 `agent.state` 等"不存在"。实测位置不同——v1 模块打在 **`app.exe` 的 PYZ 归档**里，不在 `_internal` 目录：

| 检索项 | `engine-dist/app/_internal/spectrumagent` | `app.exe`（PYZ） |
|---|---|---|
| `agent.state` / `agent.llm` | — | **存在** |
| `agent.context` / `agent.workflow` / `tools.workflows` | — | **不存在** |
| `annotation` / `api` / `data` | 存在 | — |

**结论：0.4.0 发布包含 v1 编排，不含 v2 三个新模块。** 复核的核心判断成立（重启旧安装包不会加载工作区新文件，必须重新构建并同步前端、Rust 桥、Python 引擎），但"agent 模块不存在"的表述需修正为"v2 新模块不存在"。

引擎选择见 `src-tauri/src/engine_path.rs:14`：仅 `#[cfg(debug_assertions)]` 下才读 `SPECTRUM_ENGINE_EXE` 走 `development_override`；release 走 `resolved_resource`，即打包的 `app.exe`。**所以发布版与开发版是两套产物，开发模式的验证结果不能直接代表发布版。**

另外，第二轮称"只读访问同路径 SQLite 得到 4096 字节、无业务表"。本轮在同一路径实读为 **483328 字节、29 张表、`dataset_registry` 15 行**。`-shm` 时间戳为 10-28 02:02（本轮前一次只读访问），主库未变动。**该 4096 字节结果未能复现，不能作为结论依据。**

### 7.2 引用必须带对象类型（新缺陷，已复现）

`context.py:14` 的 `user_reference` 见到"第 N 个"就返回该片段，随后被当作**数据集**引用交给 `datasets.resolve`。最小案例实测（A 为当前活动数据）：

| 用户说法 | 活动数据 | 候选 | 手势 | 标注版本 | 判定 |
|---|---|---|---|---|---|
| 对第二个数据集标注 | A → B | — | — | — | 正确 |
| 接受第二个候选 | A → **B** | 清空 | 清空 | 清空 | **错** |
| 用第二个配方做预处理 | A → **B** | 清空 | 清空 | 清空 | **错** |
| 取消，不要第二个候选 | A → **B** | 清空 | 清空 | 清空 | **错** |

连"取消"都会切数据并清空产物。根因：`context.py:37-51` 的 `select()` 在切换时清空 `candidate_ref` / `gesture_ref` / `annotation_version_id` 等，而触发切换的是一次误解析。

修复方向：引用词法必须带**对象域**——"第二个数据集 / 候选 / 配方 / 区域"分别查各自的目录快照。**候选选择与配方选择不得改变活动数据集。**

### 7.3 共享目录快照

仅统一 `ORDER BY` 不够。界面列表由 `types.ts:30` 的 `mergeRecords` 决定（按 id 合并、旧在前新追加），助手目录来自数据库全量——二者即使都声称"导入顺序"也可能是两份列表。

应让界面与助手共用同一份目录快照，记录：目录范围（项目、筛选条件）、展示顺序与对应 ID、本次列表引用标识。"第一个"按用户正在引用的那份目录解析，旧会话保留原映射。

### 7.4 独立显示名

三个概念分开存：内部 ID（关联用）、原始名称（追溯用）、显示名/用户别名（界面与对话用）。显示建议"用户别名 + 采集时间 + 读模式 + 尺寸"。

`workflows.py:88-93` 的 `safe_name()` 用 `rsplit("/",1)[-1]` 去掉目录，导致 `batch_A/同名.hdr` 与 `batch_B/同名.hdr` 变成同一显示名——复核此点成立。

重名先分类：登记表允许同一源文件以不同 `raw` 模式形成两条记录（`api/registry.py:88` 的 `UNIQUE(header_key,raw)`），因此同名**可能代表不同读取模式**，不能未核查就当重复数据合并。

### 7.5 完整任务目标与版本绑定

当前 `context.py` 只有一个 `intent`，且 `workflows.py:168-170` 在每次标注保存后统一置 `next_action=preprocess`，即使用户只要求标注。应保存完整目标：

> 当前数据 A；目标 PP 与背景；执行标注、保存、默认预处理；比较尚未请求。

版本绑定：`workflows.py:440-446` 的 `run_default` 在省略参数时查数据库**最新**标注版本并选内置配方，可能偏离"刚才保存的版本"或"刚选的 SNV 配方"。正确规则：

- "刚才保存的" → 绑定刚返回的版本；
- "用第二个方案" → 绑定该次比较中的配方版本；
- 仅当用户明确要求"最新"时才查询并固定。

`done` 只表示一轮交互结束，不能当业务完成；应另设任务状态，由真实标注版本、预处理成功状态与产物关联判定。

### 7.6 运行信息需可核对

避免以后再靠文件时间猜版本，应暴露并可查询：构建标识、引擎运行模式（`development_override` / `resolved_resource`）、工具目录版本、会话 skill 版本。界面显示"当前编排 v2"。

### 8.3 为什么本项目的 ReAct 必须收紧

6.1（L2540-2560）定义的"单轮任务的完整轨迹"是固定流程：
规划 → 计划确认(HITL) → Schema 校验 → 算子执行 → 摘要返回 → 结果解读 → 入库 → 报告 → 写项目记忆。

而 L2560-2563 的"三条不可绕过的约束"才是真红线：

| 约束 | 原文 | 对应代码 |
|---|---|---|
| ① 数值封闭 | LLM 输出中任何数字必须能在同一轮算子返回值里找到对应项，找不到则该回答被拦截重写 | `llm.py:136-152` egress 扫描 + `tools/__init__.py:237-243` 标量白名单 |
| ② 前置必检 | 每个工具声明前置条件，执行前检查（未做反射率转换则拒绝 SNV） | `tools/__init__.py` 各 `*Arguments` 校验 + `workflows.py` 各 handler 前置检查 |
| ③ 长任务异步 | 预计超 60 秒的任务强制转异步，返回任务 ID | `preprocess.run` 走队列 + `run_id` |

这三条是**领域状态机**，不是通用 agent 框架能提供的。自由 ReAct（模型自己决定下一步）恰好会破坏它们：跳过前置条件、绕过 HITL 门控、重复执行不可逆写操作。

v2 的 `workflow.py` 已经是收紧版：`MAX_WORKFLOW_STEPS=32` 预算、`AGENT_NO_PROGRESS` 无进展检测、`TASK_DATASET_MISMATCH` 目标一致性、`human_check` / `plan_check` 门控、`RECOVERABLE` 错误白名单。

### 8.4 若未来真要迁 LangGraph 的判据

当前**一条都不成立**：

1. 流程拓扑需要运行时动态生成 —— 本项目分支由**数据状态**决定（有无标签、分割是否 ready、有无可信种子、能否画布指认），图引擎要写成大量条件边
2. 跨进程 / 跨天长流程恢复 —— 已有 `agent_round` / `agent_step` 表承担 checkpointer 职责
3. 多 agent 协作 —— 单机单用户桌面应用，不需要
4. 流程图要直接暴露给用户编辑 —— 需求未要求

净收益核算：编排代码约 950 行（`workflow.py` 264 + `context.py` 196 + `tools/workflows.py` 490），迁到 LangGraph 后**红线校验一行都省不掉**（数值封闭、前置必检、标量白名单、出域扫描全是自研），净减代码接近 0；净损失是 state 序列化格式随框架版本变化，破坏历史会话回放——正是 L2387 担心的"框架升级破坏复现性"。

### 8.5 选型对照解决不了的真实缺口

前两轮已定 4 条（引用类型化 / 共享目录快照 / 任务目标与版本绑定 / 真实模型验收），本轮新增 1 条：
